    ZFS Administration

    Dataset and Filesystem Management

    In ZFS, datasets and filesystems are the core units for managing data. A dataset can be a file system, a volume (ZVOL), or a snapshot. This section covers how to create, delete, and rename datasets, configure dataset properties, and manage filesystem mounting and unmounting in ZFS.

    Creating, Deleting, and Renaming Datasets

    Creating Datasets

    In ZFS, creating a dataset within a ZPOOL is a straightforward process. Each dataset can be customized with specific properties, such as compression or quotas. To create a dataset, the zfs create command is used, followed by the name of the pool and the desired name of the dataset:

    sudo zfs create mypool/mydataset

    This command creates a dataset named mydataset inside the mypool ZPOOL. The dataset can be used like any traditional filesystem but comes with ZFS-specific features.

    Deleting Datasets

    To delete a dataset, the zfs destroy command is used. This permanently removes the dataset and all its data. Be cautious when deleting datasets, as this operation cannot be undone.

    sudo zfs destroy mypool/mydataset

    In this example, the mydataset dataset in the mypool ZPOOL is deleted. This removes the dataset and frees the associated storage.

    Renaming Datasets

    If you need to rename a dataset, the zfs rename command allows this without affecting the data or structure of the dataset. The syntax is as follows:

    sudo zfs rename mypool/mydataset mypool/newdatasetname

    This command renames mydataset to newdatasetname while keeping the dataset in the same ZPOOL (mypool).

    Setting Dataset Properties

    ZFS datasets come with various properties that can be adjusted to meet the requirements of specific workloads. Common properties include compression, deduplication, quotas, and reservation limits.

    Enabling Compression

    Compression is a valuable feature in ZFS that can save disk space without a significant performance hit, depending on the workload. To enable compression on a dataset, use the zfs set command:

    sudo zfs set compression=on mypool/mydataset

    ZFS supports multiple compression algorithms, such as lz4, gzip, and zle. You can specify the compression type as follows:

    sudo zfs set compression=lz4 mypool/mydataset

    Enabling Deduplication

    Deduplication eliminates redundant copies of data blocks within a ZFS pool, reducing storage usage. However, deduplication can have a significant impact on performance and memory usage, so it should be used with caution. To enable deduplication on a dataset:

    sudo zfs set dedup=on mypool/mydataset

    To disable deduplication later:

    sudo zfs set dedup=off mypool/mydataset

    Setting Quotas and Reservations

    ZFS provides four related properties for controlling dataset space usage: quota, refquota, reservation, and refreservation. A quota sets an upper limit on how much space may be consumed, while a reservation guarantees that a minimum amount of space remains available to the dataset. The difference between the plain and ref variants is what gets counted: quota and reservation include the space used by all descendants of the dataset — child datasets, snapshots, and clones — whereas refquota and refreservation count only the space referenced by the dataset itself.

    To limit a dataset and everything beneath it, including snapshots, to 100 GB:

    sudo zfs set quota=100G mypool/home

    To limit only the active data in a dataset, so that snapshots and child datasets do not count against the limit:

    sudo zfs set refquota=50G mypool/home/alice

    Reservations use the same naming convention. A reservation sets space aside for the dataset and all of its descendants, while a refreservation guarantees space only for the data the dataset itself references:

    sudo zfs set reservation=20G mypool/db
sudo zfs set refreservation=20G mypool/db

    The distinction matters most on datasets with snapshots. Under a plain quota, deleted files are not freed as long as an older snapshot still references them, so a user who hits the quota and deletes files may see no space returned — the dataset simply stays full. The common pattern is therefore to give users a refquota for their working data, so that the space held by snapshots is accounted to the administrator who manages them rather than to the user. Similarly, a refreservation guarantees room for new writes even when snapshots consume large amounts of space, which is why creating a ZVOL without the -s (sparse) option automatically sets a refreservation for the full volume size.

    All four properties can be inspected together with zfs get, and any of them can be cleared by setting the value to none:

    sudo zfs get quota,refquota,reservation,refreservation mypool/home/alice
NAME               PROPERTY        VALUE   SOURCE
mypool/home/alice  quota           none    default
mypool/home/alice  refquota        50G     local
mypool/home/alice  reservation     none    default
mypool/home/alice  refreservation  none    default

    Key points:

    • quota and reservation count the dataset plus all descendants, including snapshots; refquota and refreservation count only the data the dataset itself references.
    • A quota cannot be set below the amount of space the dataset currently consumes, and a reservation cannot exceed the free space available in the pool.
    • The two kinds of limit can be combined: a refquota caps a user's working data while a larger quota caps the total including snapshots.

    Per-User and Per-Group Quotas

    The quota and refquota properties limit whole datasets. When many users share a single filesystem, space can instead be limited per owner with the userquota and groupquota properties:

    sudo zfs set userquota@alice=10G mypool/home
sudo zfs set groupquota@staff=100G mypool/home

    Current consumption per user or group is reported by the zfs userspace and zfs groupspace commands:

    sudo zfs userspace mypool/home

    Key points:

    • A userquota applies only to the dataset it is set on, not to descendants, and does not count that user’s space in snapshots.
    • Enforcement is slightly delayed: because space is accounted asynchronously, a user may briefly exceed the limit before writes start failing with EDQUOT.
    • On Linux, projectquota additionally limits space by project ID, which can be attached to a directory tree with zfs project — useful when a “user” is really an application or tenant.

    Creating Volumes (ZVOLs) and Choosing volblocksize

    Besides filesystems, a dataset can be a volume (ZVOL): a block device backed by the pool, exposed under /dev/zvol/. Volumes are used where raw block storage is needed — virtual machine disks, iSCSI LUNs, or foreign filesystems on top of ZFS. A volume is created with zfs create -V and a fixed size:

    sudo zfs create -V 50G -o volblocksize=16K mypool/vmdisk

    This creates a 50 GB block device at /dev/zvol/mypool/vmdisk. By default the volume is thickly provisioned: ZFS sets a full-size refreservation so the space is guaranteed up front, as described under Setting Quotas and Reservations. Adding -s creates a sparse (thinly provisioned) volume that only consumes space as data is written.

    The volblocksize property is the volume counterpart of recordsize, with one crucial difference: where recordsize can be changed at any time, volblocksize is fixed when the volume is created and can never be changed. Every block of the volume is exactly this size. The default is 16 KB in current OpenZFS releases (older versions used 8 KB). The current value can be checked with:

    sudo zfs get volblocksize mypool/vmdisk

    Choosing the value is a balance between two failure modes. A volblocksize larger than the typical write size of the workload causes read-modify-write amplification: a database writing 8 KB pages onto a 64 KB-block volume must read and rewrite 64 KB for every page. A volblocksize that is too small wastes capacity on RAID-Z, where parity and padding overhead grows sharply for small blocks — a volume with small blocks on a wide RAID-Z vdev can consume far more space than its data would suggest. Mirrors do not suffer this overhead, which is one reason mirrored pools are generally preferred for volume-heavy workloads such as virtualization.

    Key points:

    • Because volblocksize cannot be changed, the only way to fix a wrong choice is to create a new volume and copy the data across, so it deserves a deliberate decision at creation time.
    • Match the block size to the consumer: the guest filesystem's cluster size or the database's page size. For general-purpose VM disks the 16 KB default is a reasonable choice; databases with 8 KB pages benefit from volblocksize=8K on mirrors.
    • Snapshots, clones, compression, and replication all work on volumes exactly as they do on filesystems.

    Mounting and Unmounting Filesystems

    ZFS automatically mounts datasets as filesystems at boot time, but filesystems can also be mounted and unmounted manually as needed.

    Mounting Filesystems

    By default, ZFS filesystems are automatically mounted in the /mypool directory. However, if manual mounting is required, the zfs mount command can be used:

    sudo zfs mount mypool/mydataset

    This command mounts the mydataset filesystem, making it accessible.

    Unmounting Filesystems

    To unmount a ZFS filesystem, use the zfs unmount command:

    sudo zfs unmount mypool/mydataset

    Unmounting removes the dataset from the filesystem hierarchy without deleting the data. It can be mounted again later.

    Sharing Datasets over NFS and SMB

    ZFS can manage network shares as dataset properties. Instead of maintaining /etc/exports or Samba share definitions by hand, the sharenfs and sharesmb properties attach the sharing configuration to the dataset itself: the share follows the dataset through renames and replication, is inherited by child datasets, and is activated automatically at boot when the dataset is mounted. ZFS does not replace the file servers — the NFS server and Samba must still be installed and running; ZFS only manages their configuration.

    Sharing over NFS

    The simplest form exports a dataset with default options:

    sudo zfs set sharenfs=on mypool/mydataset

    Note that sharenfs=on exports the dataset read-write to every host that can reach the server. Production shares should restrict access, which is done by setting the property to a list of export options instead of on:

    sudo zfs set sharenfs=rw=@192.168.1.0/24,ro=@10.0.0.0/8 mypool/mydataset

    This grants read-write access to the local network and read-only access to another. Active shares can be listed and controlled with:

    sudo zfs get sharenfs mypool/mydataset
sudo zfs share -a
sudo zfs unshare mypool/mydataset

    Sharing over SMB

    The sharesmb property publishes the dataset as an SMB share through Samba:

    sudo zfs set sharesmb=on mypool/mydataset

    The share name is derived from the dataset name, with slashes replaced by underscores (mypool_mydataset in this example). On Linux this works through Samba's usershare mechanism, which must be enabled in the Samba configuration; user authentication is handled entirely by Samba, so accounts and passwords are managed with the usual Samba tools.

    Key points:

    • Sharing properties are inherited, so setting sharenfs on a parent shares every child dataset the same way — convenient for a tree of home directories, surprising if a sensitive child dataset is created later and inherits the share.
    • Datasets intended for SMB clients are best created with the casesensitivity property set to mixed, which matches Windows name-handling expectations; like volblocksize, this property can only be set at creation time.
    • NFS and SMB manage their own access control on top of the filesystem permissions covered under Access Control; the effective permissions are the intersection of the two.

    Managing Snapshots and Clones

    Automating Snapshot Creation

    Snapshots in ZFS are point-in-time representations of datasets and volumes. These are efficient and instantaneous, consuming little space initially, as only the changes made after the snapshot are stored.

    Automating the creation of snapshots can be handled through cron jobs or tools like zfs-auto-snapshot. Here’s an example cron job that takes a snapshot of mypool/mydataset every day at midnight:

    0 0 * * * zfs snapshot mypool/mydataset@$(date +\%Y-\%m-\%d)

    This job creates daily snapshots with the date appended as the snapshot name. More advanced tools like zfs-auto-snapshot allow users to configure automatic snapshot retention policies for hourly, daily, weekly, and monthly snapshots.

    Snapshot Management Tools

    A bare cron job creates snapshots but never removes them, and an unpruned snapshot schedule will eventually fill the pool, since every snapshot pins the blocks it references. Production setups therefore use a dedicated tool that handles the full lifecycle: creating snapshots on a schedule, pruning them according to a retention policy, and often replicating them to another system.

    sanoid is the most widely used option on Linux (and is available on FreeBSD through packages). Policy lives in /etc/sanoid/sanoid.conf, where datasets reference reusable retention templates:

    [mypool/mydataset]
        use_template = production
        recursive = yes

[template_production]
        hourly = 36
        daily = 30
        monthly = 3
        autosnap = yes
        autoprune = yes

    Run from a systemd timer or cron, sanoid keeps exactly the configured number of hourly, daily, and monthly snapshots and prunes the rest. Its companion tool syncoid replicates datasets between hosts with a single command, working out the correct full or incremental zfs send behind the scenes and resuming interrupted transfers:

    sudo syncoid mypool/mydataset backup@backuphost:backuppool/mydataset

    zrepl takes a different approach: a single daemon, configured in YAML, that handles snapshotting, push or pull replication between hosts over TLS, and independent retention policies on each side. It suits setups where replication should run continuously rather than from periodic jobs. zfs-auto-snapshot, mentioned above, remains the simplest of the three: it is purely cron-driven, requires no configuration file, and datasets are excluded by setting the com.sun:auto-snapshot property to false.

    Key points:

    • Retention is the reason to use a tool rather than cron: decide how many hourly, daily, and monthly snapshots each dataset warrants, and let the tool enforce it. Scratch and cache datasets should be excluded entirely.
    • Snapshot automation fails silently — the job breaks, and nobody notices until a restore is needed. sanoid's --monitor-snapshots flag reports datasets whose newest snapshot is too old, and is designed to be wired into a monitoring system.
    • Replicating tools pair naturally with the techniques described in Replication; syncoid, for example, can use bookmarks so the source does not need to retain old snapshots.

    Rolling Back to Snapshots

    One of the most powerful features of ZFS is the ability to roll back to a previous snapshot, effectively returning the dataset to its previous state. This is useful in cases of accidental deletion or corruption.

    To roll back to a snapshot, the following command is used:

    zfs rollback mypool/mydataset@snapshotname

    Rolling back destroys all changes made after the snapshot, so it is a destructive operation. ZFS allows rollback to intermediate snapshots if necessary, but it requires destroying more recent snapshots to do so.

    Comparing Snapshots with zfs diff

    Before rolling back or deleting anything, it is often worth checking what actually changed. The zfs diff command lists the differences between a snapshot and the live filesystem, or between two snapshots of the same dataset:

    sudo zfs diff mypool/mydataset@snapshotname
sudo zfs diff mypool/mydataset@monday mypool/mydataset@tuesday

    Each line of output is prefixed with a symbol: + for a file that was added, - for one that was removed, M for one that was modified, and R for one that was renamed. Because ZFS answers this from block birth times rather than walking and comparing every file, zfs diff is far faster than tools like rsync -n on large filesystems.

    Deleting Snapshots and Clones

    Deleting snapshots is straightforward and helps free up storage space consumed by historical changes. Use the zfs destroy command:

    zfs destroy mypool/mydataset@snapshotname

    Deleting a snapshot frees space consumed by the changes made after the snapshot was taken, but it leaves the underlying dataset intact.

    Clones, unlike snapshots, are writable copies of snapshots. They are created using the zfs clone command and must be based on an existing snapshot. Clones are independent of the original dataset and can be promoted to become the primary dataset.

    To delete a clone, first ensure that it is not dependent on any other datasets. Then use:

    zfs destroy mypool/myclone

    Clones are a powerful feature in ZFS, allowing developers to test changes on a dataset without affecting the original data.

    Protecting Snapshots with Holds

    A hold prevents a snapshot from being destroyed, even by zfs destroy -r. This protects snapshots that must survive — a legal retention copy, or the source of an in-progress replication — from cleanup scripts and fat fingers alike:

    sudo zfs hold keep mypool/mydataset@snapshotname
sudo zfs holds mypool/mydataset@snapshotname
sudo zfs release keep mypool/mydataset@snapshotname

    Here keep is an arbitrary tag name; a snapshot can carry several holds with different tags, and it cannot be destroyed until every hold is released — attempts fail with “dataset is busy”. The -r flag applies a hold to the same-named snapshot of every descendant dataset.

    Understanding Space Accounting

    Traditional tools give misleading answers on ZFS: df shows each dataset sharing the whole pool’s free space, and du reports compressed on-disk sizes and cannot see snapshots. The authoritative view is zfs list -o space:

    zfs list -o space mypool/mydataset
NAME               AVAIL   USED  USEDSNAP  USEDDS  USEDREFRESERV  USEDCHILD
mypool/mydataset    412G  80.3G     12.1G   68.2G             0B         0B

    The USED total breaks down into four parts: USEDDS is the data the dataset itself currently references, USEDSNAP is the space that would be freed if all of its snapshots were destroyed, USEDREFRESERV is space set aside by a refreservation, and USEDCHILD is the total consumed by descendant datasets.

    Snapshot sizes deserve special care: the used value of an individual snapshot counts only the blocks unique to that snapshot. Blocks shared by two or more snapshots are counted in none of them — only in the dataset’s overall USEDSNAP. This is why destroying a single snapshot often frees far less space than expected, while destroying a range of adjacent snapshots frees more than the sum of their individual used values. The written property (and written@snapshot) reports how much new data was written since the previous snapshot, which is usually the number people are actually looking for.
